# 협업 프로토콜 — 3인 풀스택 팀 운영 규약

누가 무엇을 소유하는가, 어디까지 다 같이 알아야 하는가, 다음 단계로 언제 넘어가는가.

---

## 1. "안다"의 세 단계

전부 똑같이 알 수는 없고, 필요도 없습니다.

| 단계 | 기준 | 확보 목표 |
|---|---|---|
| 설명 | 화이트보드에 그리고 왜 그랬는지 말할 수 있다 | 전원 × 전 영역 |
| 디버깅 | 로그 보고 원인 계층을 특정하고 고칠 수 있다 | 전원 × 전 영역 |
| 구축 | 빈 화면에서 처음부터 만들 수 있다 | 소유자 + 최소 1명 |

면접에서 요구되는 건 사실상 **설명·디버깅**입니다. **구축**까지 전원을 목표로 잡으면 프로젝트가 안 끝납니다.

## 2. 역할 — 소유는 최종 책임이지 독점이 아님

| | A — 플랫폼/주행 | B — 임무/관제 | C — 인식/인터랙션 |
|---|---|---|---|
| 소유 | `robot/`, `sim/` | `fleet/`, `comms/`, `interfaces/` | `perception/`, POI, 월드 자산 |
| 핵심 | URDF, ros2_control, CAN FD, Nav2, SLAM | 임무 상태머신, VDA5050, Open-RMF, Zenoh | VLM, POI 매핑, 뎁스 카메라, 센서 배치 |

**`interfaces/` 변경은 3인 승인 필수.** 세 축이 만나는 유일한 지점이라, 여기만 잠그면 나머지는 각자 빠르게 가도 안 깨집니다.

## 3. 전원 풀스택 장치 3개

### ① 디버그 우선권 역전
어느 영역에서 버그가 나오든 담당자가 아닌 사람이 먼저 봅니다. 일정 시간 안에 못 잡으면 소유자에게 넘김. 비용이 거의 없고 효과가 가장 큽니다.

### ② 통합 당번 로테이션
통합 사이클마다 당번 한 명. 당번의 일은 자기 축 개발이 아니라 이것들입니다.

- CI 복구
- 올라온 버그 재현하고 원인 계층 특정해서 배정
- 통합 브랜치에 세 축 붙여 임무 완주시키기
- `trace.md` / `troubleshooting.md` 갱신
- 다른 두 사람에게 "질의부터 모터까지 어디를 거치나 / 왜 그렇게 정했나 / 뭐가 실패했나" 질의, 막힌 답은 `faq.md`로

당번 사이클엔 자기 축 산출이 안 나온다고 계획하세요.

### ③ 1인 완주 리허설 (최종 검증)
각자 깨끗한 머신에서 혼자, 도움 없이 전체를 세우고 임무를 완주시킨 뒤 카메라 앞에서 설명합니다. 막힌 지점이 곧 지식 공백 목록이고, 그걸 메우면 준비 끝입니다.

## 4. 진척 게이트

시간이 아니라 통과 조건으로 넘어갑니다. 게이트를 못 넘으면 다음으로 안 갑니다.

### G0 — 계약 (전원 공동)
- 산출물: interfaces 패키지, POI 스키마, stub 노드, CI, Docker, `trace.md` 뼈대, ADR 3장
- 통과 조건: CI 초록 + stub 위에서 GuideTask 한 건이 goal→result까지 완주
- stub 노드가 핵심입니다. NavigateToPose를 받아 몇 초 뒤 성공/실패를 반환하고 RobotStatus를 발행하는 200줄짜리 노드 — 이게 있어야 B와 C가 A를 기다리지 않습니다.

### 병렬 트랙 (G0 통과 후 분기)

| | A | B | C |
|---|---|---|---|
| 1차 | **G1** primitive URDF + ros2_control + mock_components → cmd_vel로 오도메트리 갱신 | **G3** 임무 상태머신 (stub 위) → stub 기준 10F→11F 시퀀스 완주 | **GC1** Gazebo 월드(10F·11F·로비) + POI 레지스트리 → A가 그 월드에서 맵 생성 가능 |
| 2차 | **G2** 월드 맵 생성 + Nav2 단일 층 → 한 층에서 POI까지 자율 도달 | **G4** VDA5050 어댑터 + Open-RMF → 외부 대시보드에 로봇이 잡힘 | **GC2** 센서 배치 확정 + 자연어→POI 검증 계층 → 미등록 질의를 정확히 거절 |

### G5 — 통합 (전원 공동)
- 산출물: stub를 실제 Nav2로 교체, 층 전환·맵 전환·재측위 결합
- 통과 조건: 시뮬에서 10F→11F 임무 완주, **10회 연속 성공**
- 프로젝트에서 가장 어렵고 세 계층 지식이 다 필요한 구간입니다. 셋이 붙는 게 교차학습 효과도 제일 큽니다.

### G6 — 실물 (메쉬 도착 이후, A만 해당)
- 산출물: 메쉬 교체 + 관성 갱신 + CAN FD 하드웨어 인터페이스
- 통과 조건: 실물이 cmd_vel로 주행, 시뮬과 같은 launch 경로
- 메쉬는 **A의 G6만** 막습니다. 나머지 전부 무관하니, A는 CAN FD 벤치 테스트를 지금 시작하세요 — 모터와 드라이버만 있으면 됩니다. 여기가 제일 안 될 확률이 높은 구간이라 리스크를 앞으로 당기는 게 맞습니다.

### G7 — 완료 (전원 공동)
- 산출물: 실물 임무 20회 시행 + 측정 + 1인 완주 리허설 3인 통과 + 영상·문서
- 통과 조건: `mission.md` 성공 기준 충족, 세 사람 모두 혼자 완주 및 설명 가능

## 5. 레포에 남는 것 = 면접 자료

| 문서 | 소유 | 답하는 질문 |
|---|---|---|
| [mission.md](mission.md) | 공동 | 뭘 하는 프로젝트인가 |
| [trace.md](trace.md) | 공동 | 질의부터 모터까지 어디를 거치나 |
| [adr/](adr/) | 결정자 | 왜 그 선택을 했나 |
| [troubleshooting.md](troubleshooting.md) | 공동 | 뭐가 안 됐고 어떻게 알아냈나 |
| [benchmarks/](benchmarks/) | 당번 | 얼마나 잘 되나 |
| [faq.md](faq.md) | 공동 | 상호 질의에서 나온 것들 |

- **trace.md** — 임무 한 건이 통과하는 전 경로를 홉마다 노드·토픽·파일과 함께 적고, 각 홉에 "여기서 실패하면 어떻게 되는가"를 한 줄씩. 이걸 안 보고 화이트보드에 그릴 수 있으면 면접 준비는 끝입니다.
- **troubleshooting.md** — 문제당 네 줄: 증상 / 원인 / 해결 / 알아낸 방법. 마지막 줄이 가장 변별력 있는 면접 질문의 답입니다.

## 6. 비용

장치 세 개를 다 돌리면 게이트 통과가 더 오래 걸립니다. 그만큼 스코프를 깎으세요 — 로봇 대수를 줄이든, Open-RMF를 G4에서 빼서 후순위로 미루든.

바꿀 만한 거래입니다. 기능 하나 더 있는 프로젝트보다, 세 사람 다 전체를 자기 것으로 말할 수 있는 프로젝트가 훨씬 크게 작용해요.
